# 概要

Hacker News 用户讨论了新发布的 Cursor CLI，并就 AI 编程代理、工具标准化以及开发者工作流程的未来展开了辩论。

# IDEAS:

*   使用特定文件名（如 CLAUDE.md）作为一种在代码库中进行品牌营销的巧妙策略。
*   IDE 是为人类开发者设计的，而自主编程的 AI 代理并不需要图形用户界面。
*   未来 IDE 的角色将转变为管理和审查 AI 生成的解决方案，而非手动编码。
*   命令行工具比完整的 IDE 插件更具可组合性，也更加便携，能跨多种环境工作。
*   开发者不断切换工具的现象，正反映出当前 AI 编程领域仍处于非常不成熟的阶段。
*   大型语言模型可能会因其训练数据集中于流行框架，从而抑制新编程框架的普及和采用。
*   一个核心争论在于，是选择模型中立的工具，还是选择与特定模型深度绑定的工具。
*   模型提供商和工具构建者之间，正在就谁能提供主要的开发者交互界面而展开激烈竞争。
*   允许大型语言模型直接访问文件系统，带来了便利性与巨大安全风险之间的根本性权衡。
*   编程工作的本质正从编写代码转变为审查、质量保证以及对 AI 进行迭代式提示。
*   AI 代理生成的代码需要新的审查工具，能够将变更按逻辑单元进行分组和展示。
*   将文档写入单独的子系统文件中，作为上下文传递给下一个接触该部分的 AI 代理。
*   采用符号链接作为一种临时解决方案，将标准化的 `AGENT.md` 链接到特定工具的文件。
*   开发者可以利用一个 AI 代理来自动验证另一个 AI 代理完成的工作和假设。
*   基础模型正逐渐商品化，而用户体验（UX）将成为编程工具之间真正的差异化优势。
*   人们担心，过度关注 AI 代理工作流可能会损害传统开发体验的质量和严谨性。
*   如果一份文档能够让最先进的 LLM 感到困惑，那么它几乎肯定也会让普通开发者感到困惑。
*   CLI 代理的主要优势在于，它让你能使用自己喜欢的编辑器，而不是被锁定在某个复刻版里。
*   为人类贡献者和 AI 代理分别维护不同的文档，是一种提高清晰度的有效方法。
*   不同的 AI 交互模式会带来不同的心智负担，例如单步修改对比批量变更。
*   AI 代理有时像个初级开发者，不经讨论就直接丢给你一大堆需要审查的代码。
*   开发者的角色正在演变，从管理其他程序员，转变为管理和引导 AI 代理。
*   CLI 工具是 AI 开发生态系统中的一个“窄腰”，连接着各种工具和服务。
*   AI 代理需要一个沙箱环境来运行，以确保它们不会对系统造成意外的损害。
*   特定于模型的配置文件（如 CLAUDE.md）会被放置在系统提示之后，作为会话的初始输入。
*   与其使用生成代码的 AI，我们或许更需要一个本身确定性但使用 AI 的代码生成器。
*   我们不应创建特定于 AI 的命令行方言，因为这些工具的重点是理解自然语言。
*   将工作流分解为多个步骤，并在每个步骤中使用不同的模型，可以获得更好的结果。
*   模型提供商之间的激烈竞争，正在推动一个更加注重用户体验和工具创新的生态系统。
*   编程的未来不仅仅是自动化，而是人与 AI 之间一种更深层次的协作关系。

# INSIGHTS

*   AI 代理正将开发者的角色，从代码编写者转变为代码审查者、规划者和提示工程师。
*   开发者心智份额的争夺战，正从传统 IDE 转向 AI 代理的用户体验和工作流。
*   模型提供商与工具构建者，正在激烈竞争成为开发者与 AI 交互的主要接口。
*   像 `AGENT.md` 这样的标准化努力，正在与品牌差异化策略（如 `CLAUDE.md`）进行博弈。
*   基于 CLI 的代理提供了更大的灵活性，使开发者摆脱特定 IDE，重新定义了开发环境。
*   一个 AI 代理的最终效能，在很大程度上取决于用户分解问题和编写高质量提示的能力。
*   AI 代理带来的便捷性与它们对文件系统访问所带来的固有安全风险之间，存在着根本性的矛盾。
*   AI 编程工具的不断变化，反映了一个虽然不成熟但正在以惊人速度演进的技术领域。
*   大型语言模型本身正在商品化；长期的价值将存在于围绕它们构建的用户体验和工具中。
*   未来 IDE 的核心功能可能会演变为管理、可视化和回滚 AI 代理的工作，而非手动编码。
*   为 AI 代理准备的文档质量，直接影响其性能、可靠性和完成复杂任务的能力。
*   通过支持独立的、模型中立的工具，可以促进模型提供商之间的良性竞争，避免用户被锁定。

# HABITS

*   使用 `git` 和 `git worktrees` 来管理来自并行的 AI 代理会话的变更。
*   依靠 `lazygit` 或其他差异比较工具，来审查由 AI 代理生成的代码。
*   始终将 `README.md` 添加到代理的上下文中，以强制保持项目文档的最新状态。
*   创建从 `AGENT.md` 到特定文件的符号链接，如 `CLAUDE.md`，以实现标准化。
*   为 CLI 代理使用别名，自动指示它们读取一个集中的 `AGENT.md` 指令文件。
*   有选择地将较小的上下文文档 `cat` 在一起，以指导代理完成特定的任务。
*   利用会话启动钩子，自动将会话所需的特定文件添加到 AI 代理的上下文中。
*   将文件内容直接通过管道传送给 CLI 代理，以提供上下文，避免不必要的工具调用。
*   在处理日常工作时，让一个基于终端的代理在后台持续运行以完成任务。
*   审查代理所做的每一项更改，从不以完全放手的方式信任它的工作。
*   为确保安全，在专用的虚拟机或沙盒环境中运行具有文件系统访问权限的编码代理。
*   配置代理，使其将变更分组为逻辑单元，以便于审查和创建有意义的提交。
*   为 Cursor 设置规则，使用“计划-方案-执行”模式，以实现更清晰的变更管理。
*   当代理的执行路径偏离预期时，要频繁地中断其流程并及时纠正方向。
*   使用 `Emacs + Magit` 的强大组合，来监控由 AI 代理传入的变更。
*   重新调整你的 Vim 设置，优先考虑 Git 插件，而不是传统的编辑效率工具。
*   当一个模型在某个问题上卡住时，尝试在工具内切换到另一个基础模型。
*   手动添加“共同作者”信息进行署名，而不是让代理自动生成提交信息。
*   使用一个专门的“Cursor 专家”代理，来验证由 Claude Code 完成的工作。
*   在 CLI 代理工作时，使用 IDE 进行持续的测试和捕捉细微的错误。
*   在你的工具设置中，禁用自动添加共同作者署名的功能，以减少版本历史中的干扰。
*   在开始一项任务之前，首先要求 AI 代理阅读相关的规划和架构文档。
*   利用终端来运行代理，这样你就可以在自己喜欢的 IDE 或编辑器中工作。
*   为了更好地控制，将复杂的任务分解成更小的步骤，并分别指导代理完成它们。
*   将代理生成的上下文信息块（context nuggets）转存到特定的 Markdown 文件中，供其他代理使用。

# FACTS:

*   使用 `CLAUDE.md` 等独特文件名，是品牌在代码库中获得可见性的一种营销策略。
*   为代理指令使用不同的文件名，可以用于数据分析，例如在 GitHub 上搜索使用统计。
*   Claude Code 的主要创建者 Boris Cherny，曾短暂加入 Cursor，后又返回 Anthropic。
*   Gemini CLI 在 Apache 许可下发布，使得竞争对手可以轻松地克隆其功能。
*   `robots.txt` 标准由 RFC9309 正式定义，展示了标准化在技术领域中的强大力量。
*   在流行框架上训练的 LLM，可能会无意中将这些框架的代码片段插入到其他项目中。
*   AI 生成的拉取请求通常存在缺陷或毫无用处，反而增加了开源项目维护者的工作量。
*   据称 Anthropic 曾表示 IDE 将会过时，因此没有计划构建“Claude GUI”。
*   Gemini CLI 在 macOS 上支持原生沙盒，这是代理工具的一个关键安全特性。
*   Cursor 的 CLI 支持 `AGENT.md`，同时也支持其专有的 `Cursor Rules` 格式。
*   通过管道将文件内容输入 Claude (`cat file | claude`)，可能因跳过工具调用而节省令牌。
*   Claude Code 可以通过像 LiteLLM 这样的工具，来使用非 Anthropic 的模型，例如 GPT-5。
*   `AGENT.md` 规范允许在子目录中放置多个文件，这与 `CODEOWNERS` 的工作方式类似。
*   在合并多个指令文件时，许多工具只是简单地将它们串联成一个更长的提示。
*   一些开发者认为，由 LLM 编写的 Git 提交信息，其质量往往优于人类编写的。
*   即使用户提供自己的 API 密钥，Cursor 仍然会通过其服务器路由所有流量。
*   Elixir 社区提出了一个标准化使用规则的想法，这与 `AGENT.md` 的概念相似。
*   用户报告称，在使用 Codex CLI 工具时遇到了登录失败和 SSL 证书验证错误。
*   OpenAI 的组织验证策略，限制每个 ID 每 90 天只能验证一个组织。
*   像 Claude Code 这样的编码代理，会自动在 Git 提交中添加“Co-authored-by”信息。
*   对于最终用户来说，大多数 AI 工具都很难追踪到最终组装完成的完整提示内容。
*   `AGENT.md` 规范建议，工具应合并配置，其中更具体的文件优先于通用文件。
*   Cursor 的产品页面提到了 `AGENTS.md`（复数），这可能是一个拼写错误或不同的规范。
*   通过 API 计费时，Claude Code 的成本可能非常高，尤其是在大规模使用时。
*   一些用户发现，Claude Code 有时也会忘记 `CLAUDE.md` 文件中给出的指令。

# ONE-SENTENCE TAKEAWAY

CLI 编码代理的兴起，正将软件开发从手动编写代码，转变为审查和引导 AI 输出。

# RECOMMENDATIONS

*   采用一个标准化的 `AGENT.md` 文件，为所有 AI 编码代理提供一致的指令。
*   使用符号链接，将特定模型的指令文件（如 `CLAUDE.md`）指向一个主 `AGENT.md` 文件。
*   在提交变更前，务必使用 `lazygit` 等差异比较工具来审查代理生成的代码。
*   为获得最高安全性，请在沙盒环境或专用虚拟机内运行 AI 代理工具。
*   选择像 Cursor 这样模型中立的工具，以避免供应商锁定并始终能使用最佳模型。
*   将 `git` 和 `git worktrees` 集成到你的工作流程中，以安全地管理多个 AI 会话。
*   努力提升你的提示工程能力，因为这对从代理获得高质量结果至关重要。
*   如果你想完全控制提交历史，请禁用在提交信息中自动添加署名的功能。
*   利用像 LiteLLM 这样的工具，将你喜欢的代理连接到不同的模型提供商。
*   强制你的代理阅读项目的 `README.md` 文件，以帮助保持文档的实时性和有效性。
*   选择一个允许实时反馈和交互的代理，并将其视为一个协作式的编程伙伴。
*   不要完全信任 AI 代理；始终监控它们的工作，并准备好随时进行干预。
*   如果你维护一个开源项目，请警惕那些由 AI 生成的低质量拉取请求。
*   积极参与代理指令的标准化工作，以改善整个生态系统，让所有人都受益。
*   建立一个专门为审查代理生成的代码（而非人类编写的代码）而优化的代码审查流程。
*   利用代理创建文档文件的能力，来维护项目的状态、决策和历史记录。
*   当一个代理陷入困境时，尝试切换其底层的语言模型以寻求不同的解决方案。
*   使用会话启动钩子，来自动化为你的代理加载上下文和初始指令的过程。
*   通过管道直接向 CLI 代理输入上下文，以绕过可能出错的工具调用过程。
*   为提高代理的性能，将大型复杂问题分解为一系列更小、更易于管理的子任务。
*   为获得更好的控制，使用具有“计划-方案-执行”模式的代理，以实现清晰的变更可见性。
*   使用基于 CLI 的代理，将自己从特定的 IDE（如 VSCode）中解放出来。
*   为你项目的不同子系统，创建单独的、详细的入门文档，供 AI 代理使用。
*   如果你关心隐私和成本，请选择支持本地 LLM 模型（如通过 Ollama）的工具。
*   将代理视为一个需要指导的初级开发者，而不是一个可以完全自主工作的专家。
